# Internal GitHub Actions interfaces

The Action supports status-only reporting. The internal capability entry `action private-reporting` returns `status-only-v1`; the composite checks it without credentials before using the optional `status-only` argument on `action plan` and `action summary`. Private plan failures replace raw error text with a fixed diagnostic. Private Summary validates the complete report, then publishes only its closed outcome and bounded managed count, without values, actor context or raw diagnostics. After a successful private Summary write, stdout carries only `plan-outcome=OUTCOME` for the step output. Detailed Summary keeps its existing silent interface and output.

Detailed Ruleset presentation includes only declaration-owned fields. Its credential-free Summary may show declared non-secret values while omitted Ruleset conditions, bypass actors and rule attributes remain absent. The mutation path still retains the complete observed Ruleset separately.

The Action removes ephemeral reports in an `always()` step after success or ordinary failure, before publishing any successful Action outputs. Cleanup failure withholds all public success outputs. File/report failures remain failures, and a nonzero original plan status takes precedence over presentation errors. Tests cover hidden Ruleset policy, canary diagnostics, malformed reports, output/storage failures, old-package refusal before authentication, all three successful outcomes and cleanup. Hosted candidate scenarios exercise private changed, read-failure and invalid-config paths through the real same-source composite. This is not publication or live credential evidence.

Normalized workflow and public-fork approval changes carry optional `normalization` metadata with required string `path`, `raw_value` and `fallback` members. The closed field-specific Actions constructor validates the field, projected value, fallback and raw token before allowing effective-value equality to remain actionable. Metadata on unrelated comparisons is rejected. Detailed CLI/Summary display the UI field and choices with a projection warning and write-required note; status-only reduction retains only its existing outcome/count boundary. These observations are presentation data, never apply input.

Normalized Issue/PR creation policies carry the same strict scalar metadata in their repository `changes` entries. The closed creation-policy constructor permits only those two native fields, matching YAML path/default, effective `ALL`, unsupported raw strings and supported desired values. Ordinary equal pairs remain invalid in reports. One policy counts as one native managed field. Normalized CLI/detailed Summary use UI choices and escaped raw warnings; status-only retains only outcome/counts. Metadata on unrelated fields/types/sections and forged evidence is rejected.

Normalized Secret Protection and Push protection changes carry optional `security_status_normalization` in their `security` entries. Required `path` and `raw_value` are strings; required `fallback` is boolean, preserving explicit false and empty raw status. The closed constructor validates control identity/default/effective value and unsupported raw status before retaining equal booleans as actionable. Wrong sections, simultaneous string normalization, forged records, duplicates and inconsistent desired pairs fail. UI warnings escape raw strings; before/after/fallback stay unquoted booleans. Detailed Summary shares CLI decisions and status-only suppresses values. This same-version protocol never supplies apply intent.

Normalized merge/squash observations use a separate `commit_messages` array with closed `menu`, UI `after` and paired `normalization` metadata (`path`, `raw_title`, `raw_message`, `fallback`). All metadata strings are required, including explicitly empty acquired raw members. Validation reconstructs one typed menu decision, rejects unsupported or inconsistent provenance, duplicates and overlapping native component changes, and counts two managed native members per menu. Equal effective before/after values remain actionable. Detailed Summary uses the same UI warning and decision as CLI, HTML-escaped; status-only exposes only its existing outcome/count boundary. This remains same-version presentation data and does not finish the wider UI count/report audit in #481.

Normalized Pages folders carry optional string `normalization` metadata on `pages.source.path` entries only. The closed constructor requires the exact Select folder UI path, `root` fallback, effective `/`, an unsupported raw folder and an active canonical desired folder. It rejects inactive source, unrelated fields, forged records, duplicates and invalid mode transitions. Required strings preserve explicitly empty acquired raw folders. An unchanged projected folder remains actionable. A source pair counts two managed native fields even when its branch is unchanged and absent from comparisons; report validation requires that minimum plus other entries, without counting a changed branch twice. Detailed Summary shares the escaped UI warning and write-required decision; status-only suppresses values. These same-version reports never supply apply intent and do not complete #481.

Normalized Pages mode entries use the same required string metadata on `pages.build_type`, through a separate closed constructor. Require the Source UI path, `deploy_from_a_branch` fallback, effective `legacy`, an unsupported raw mode and canonical desired `legacy/workflow`. Reject inactive or forged mode entries. Reconstruct actionable `legacy → legacy` without inventing inactive source; real `workflow → legacy` transitions still require both inactive source components. A mode counts one field. Mode plus source intent counts three native fields even if an unchanged source component is absent from comparisons; normalized-only minimum validation accounts for it without changing ordinary report contracts or double-counting both changed components. Mode and folder records remain independent. Detailed Summary retains exact escaped raw warnings, UI decisions and workflow deactivation; status-only suppresses both records' values.

## Scope

This page is for contributors changing the composite Action or its Go adapters. Consumers should use the [public Action guide](../github-actions.md) and the four [settings commands](../commands.md); the internal interfaces below are same-version wiring, not an independent compatibility API.

This page describes current Go interfaces, including typed label operations and merge-method booleans. See the [consumer package boundary](../github-actions.md#labels-and-permissions). Source protocol tests use the built candidate binary.

The [composite Action](../../action.yml) installs one verified Go executable, resolves metadata, runs the selected command, renders a plan Summary when needed, then publishes success outputs. The plan report is temporary presentation data. The same executable owns metadata and Summary rendering; shell owns installation bootstrap and Actions wiring. [ADR 0023](../adr/0023-public-composite-action.md) records the public packaging decision, and the [testing guide](testing.md) describes verification boundaries.

## Source Actions metadata

The CLI provides `gh settings action metadata` for same-version CLI/Action wiring. This is separate from the four settings commands. The composite invokes it through the verified executable. It resolves the current consumer checkout, including subdirectories, using the shared Go origin rules and ignoring `GH_REPO`. Neither the executable directory nor an Action source directory selects the target; no `GITHUB_WORKSPACE` override mode is added. No settings file, token or API request is needed.

Success emits exactly four single-line `key=value` records: `config-sha` is the checkout's resolved commit, `target` is its origin's owner/repository, `cli-version` is the injected executable version and `cli-sha256` is the SHA-256 of the actual executing binary. No binary-path or version argument selects a different identity. Missing identity or CR/LF in its components fails before output; output errors also return a nonzero status with a stderr diagnostic. Write failures can leave partial output. This interface adds no old-CLI fallback or multi-version protocol. See the [metadata behavior and tests](../features/actions.feature.md#rule-source-metadata-identifies-the-consumer-and-executing-binary).

On the supported Linux runner, the digest reads the running image through `/proc/self/exe`, so replacement or deletion of its launch pathname does not select other bytes. Failure to read that reference fails the command. Other platforms use the executable pathname for native development checks and require that path to remain unchanged; this does not extend the Action's supported platforms.

## Source Actions plan report

The CLI provides `gh settings action plan REPORT_PATH` for same-version Actions presentation. It runs shared application planning once and writes JSON instead of terminal plan text. Supply a caller-owned runner-temporary path with an existing parent; new files use mode 0600. Success is silent and exits zero. Missing arguments or unavailable storage fail visibly; a planning failure remains nonzero even after its report is written. Write failures can leave partial output.

The [Actions-owned report](../../internal/actions/plan.go) has these fields:

| Field | Meaning |
| --- | --- |
| `outcome` | `changed`, `no-difference`, `unmanaged`, `invalid-config`, `target-failure` or `read-failure`. |
| `target` | Available origin owner/repository; omitted for unmanaged, validation or target-resolution failure. |
| `managed` | Number of managed fields/collections in a successful comparison; nonempty label selections count once, empty labels count zero. Zero on failure does not mean unmanaged. |
| `changes` | Ordered repository/topic field/before/after entries; values remain native strings, booleans or topic string arrays. Field paths are `repository.FIELD` or `topics.names`. Empty comparisons, failures and label-only changes use an empty array. |
| `labels` | Optional typed create/update entries with `operation`, identity name, update `id`, and complete supported `before`/`after` objects. Omitted when no label operations exist. The ID-based format is unreleased. |
| `diagnostic` | Static categorical failure text; omitted on success. No raw error, token, environment dump or request header is serialized. |

Validation precedes target resolution and API access. Valid unmanaged declarations succeed locally without origin or credentials. Read failures include the already-resolved target; ordinary stderr diagnostics retain their existing text. The report is ephemeral presentation data, never apply input. The composite calls this entry with its explicit read token, then passes the report to a separate credential-free Summary step. Shared planning owns validation; no separate CLI validation call, multi-version format or saved-plan execution is introduced. See the [report behavior](../features/actions.feature.md#rule-source-planning-writes-ephemeral-typed-presentation-data).

### Actions policy entries

Current source adds optional `actions`, an ordered array of the eight closed `actions.FIELD` paths and native `before`/`after` values. Each declared field counts once, including an empty patterns list. Only inactive selected fields may have `before: null`: it means unobservable, not YAML null or an observed default. All three unavailable fields must accompany a nonselected-to-selected policy change. Summary validates types, exact enums, counts, duplicates, no-op changes and this transition as a unit. Default workflow permissions require known read/write enums and approval booleans on both sides; they do not acquire nullable-before semantics. Pattern arrays preserve order and duplicates; they do not use topic-set canonicalization. This is same-version presentation data, never apply input.

### Label plan entries

The [labels report adapter](../../internal/actions/labels.go) keeps operation identity separate from attribute objects. Complete supported objects contain `name`, `color` and `description`, including the fixed empty description default. Only selected objects appear; unlisted objects remain unmanaged.

| Operation | `before` | `after` |
| --- | --- | --- |
| `create` | Absent | Complete desired supported object; ID absent. |
| `update` | Complete observed supported object | Complete desired supported object; positive matching ID required. |

The application emits creates/updates in stable label identity order and never implicit deletes. Report validation rejects unknown/null attributes, malformed operation fields, duplicate names/IDs, incomplete objects, invalid colors/descriptions and no-op updates. ID-selected rename is supported; identity name refers to the prior name. Colors must be lowercase. When label operations exist, the managed count must be at least the number of repository/topic change entries plus one; the actual count includes all declared fields and collections. A changed outcome may contain label operations alone. This is ephemeral presentation data, never apply input.

## Source Actions Summary

The CLI provides `gh settings action summary REPORT_PATH SUMMARY_PATH`. It reads the same-version typed report and explicit nonsecret run metadata, then appends review content to the caller-owned Summary path. It requires no checkout, settings file, credentials or API access and writes no GitHub outputs. The composite invokes this verified entry in a separate step with both token variables unset. Original nonzero plan status is preserved; otherwise Summary status determines success. The four public outputs follow both required stages.

The metadata allowlist is `SETTINGS_ACTOR`, `SETTINGS_TRIGGERING_ACTOR`, `SETTINGS_EVENT`, `SETTINGS_RUN_ID`, `SETTINGS_RUN_ATTEMPT`, `SETTINGS_WORKFLOW_REF`, `SETTINGS_WORKFLOW_SHA`, `SETTINGS_CONFIG_SHA`, `SETTINGS_TARGET`, `SETTINGS_CLI_VERSION` and `SETTINGS_CLI_SHA256`. All are required. `SETTINGS_ACTION_REPOSITORY` and `SETTINGS_ACTION_REF` must either both be present or both absent; absence displays an honest local-checkout identity. Other environment values are not inspected or included.

Run ID and attempt must be positive integers, workflow/configuration revisions 40 hex characters and the CLI digest 64 hex characters. Workflow references contain an owner/repository/path and `@refs/` reference; target and optional Action repository contain owner/repository. The file entry requires an explicit non-null `managed` count from zero through fifty in current source (twenty-four repository fields, topics, labels, Rulesets, Environments, fourteen Actions policy fields, three security fields and five Pages fields); published v0.16.0 retains twenty-one and earlier packages retain their documented lower limits. The renderer rejects inconsistent report states, counts or targets, mismatched categorical failure diagnostics, unknown or duplicate fields, no-op changes and field/value-type mismatches for the supported fields. Topic arrays must be sorted, unique and valid, and equality is checked without comparing slices as interface values. Empty strings and false remain valid change values for their existing fields. Squash and normal merge commit title/message changes require supported string enums on both sides; empty, unknown or wrongly typed values are invalid. Workflow links use the workflow repository/revision; configuration links use the explicit target/configuration revision. Original and rerun actors, Action identity and CLI identity remain distinct.

Repository field names, native types, enum policies, and the scalar field count come from the [static settings definitions](../../internal/settings/repository_fields.go). Report validation adds one managed unit each for topics and labels; report-state and collection validation remain in `internal/actions`.

The JSON DTO is converted once into a private validated report containing native `settings.Change` values and a `settings.LabelChanges` sequence. Validation retains the checked outcome, diagnostic, counts, topic arrays, and label attribute presence. Rendering consumes this result through typed visitors, without inferring types from JSON values or reconstructing label operations. Metadata validation and Summary file appending retain their separate boundaries.

The [pure renderer](../../internal/actions/summary.go) classifies typed outcomes rather than terminal sentences. It quotes HTML and multiline data, retaining native observed/desired values and the apply overwrite warning. Current-source label operations use explicit create/update names and ID identity; no implicit deletion is represented. Label membership is reconciled against fresh state during apply, so the report does not bind later operations. Missing/malformed input or required metadata fails before opening the destination, preserving existing content. A blank-line separator starts the appended section even when prior text has no trailing newline. New files use mode 0600; append, write and close failures return nonzero, without atomicity or rollback guarantees. Success is silent. A valid failed-plan report is rendered and appended but still exits nonzero. Rendering/writing does not prove that GitHub published the Summary; review it before separately authorizing apply. See the [Summary behavior](../features/actions.feature.md#rule-source-summary-renders-typed-review-data-without-credentials).

Current unreleased Rulesets operations use a separate `rulesets` array of create/update operations and complete supported before/after objects. Creates have no ID; update objects both carry the same positive declared REST ID and may rename. Validation rejects null/unknown/incomplete policy, no-op updates, duplicate names/IDs, delete operations, incorrect ordering and inconsistent counts. CLI/Summary expose selected supported settings and fixed-default changes, not unlisted objects. This same-version ephemeral protocol is neither apply input nor a stable cross-version format; published older packages retain their documented projection contract.

Current unreleased Environments use a separate `environments` array with complete supported create/update policies and name identity, without numeric Environment IDs. Explicit null branch policy is valid and required in report objects; missing required values are not filled with YAML defaults. Validation rejects unsupported/delete/no-op operations, duplicate/unordered names, noncanonical/unknown keys and inconsistent outcomes/counts. CLI/Summary show default-derived changes; status-only reporting hides identities and values after validating the same closed report.

Current-source Secret scanning and private vulnerability reporting comparisons use a separate optional `security` array of closed field identities and known native booleans. Reconstruction rejects unknown/candidate fields, null/wrong types, ordinary no-op/duplicate changes, inconsistent desired pairs and managed-count underflow. CLI and Summary share the security formatter; these ephemeral values never authorize apply.

Current-source retention adds a native integer Actions comparison. Configured days remain known on both sides; null/unavailable values are forbidden. Reconstruction accepts bounded whole JSON numbers and normalizes them to native integers, rejecting strings, fractions, nonfinite/out-of-range values, no-ops and read-only maximum fields. No JSON decoding change is applied to unrelated report types.

Fork workflow policies add five closed Actions paths: the contributor approval enum and four nested native booleans under `actions.private_fork_workflows`. Both sides must be known and correctly typed; null/unavailable before values, unknown enums/paths, duplicates and no-op changes are rejected. The managed count includes each declared value, independently of whether its operation changes state. The shared formatter exposes credential decisions without reading token/secrets contents. Reports never become apply inputs.

Normalized execution radios use a separate `actions_execution` array with required UI `before`, `after` and scalar `normalization`. The closed constructor permits only genuine unknown-policy provenance and known Disable or projected Allow all before choices. Validation rejects duplicate radios, overlapping native enabled/allowed changes, forged provenance and incomplete selected transitions. Disable counts one native field; enabling counts two, plus three required unavailable selected companions on transition. A derived selected-policy component exists only in local validation, never as a duplicate rendered/serialized decision. Visible projections share escaped warnings and write-required output; known Disable before choices reveal no latent raw value or fallback label. Status-only remains value-free. This protocol is ephemeral presentation data, never apply input, and does not complete #481.

Normalized Ruleset updates carry optional `enforcement_normalization` on their existing `rulesets` entries. Required string metadata preserves empty acquired raw values. Closed reconstruction requires an update with consistent positive before/after ID. Enforcement metadata requires complete effective Disabled before-policy, a genuine out-of-UI enforcement token and canonical Active/Disabled desired status. Reject create/unbound/forged evidence, duplicates and equal ordinary objects without provenance. The writer retains selected whole effective policy while omitting write-only dismissal values; detailed Summary shares escaped ID/name warning, UI decision and explicit effective-policy label. Status-only suppresses raw/object context. Existing nonempty Rulesets collection counts once; this does not complete #481. Reports remain same-version presentation data, never apply or verification input.

Normalized Quality updates additionally carry optional `quality_severity_normalization` on the same Ruleset entry. A fixed `RulesetNormalizations` aggregate retains independent enforcement and Quality records. Each present enforcement/Quality metadata object requires all string members, including an empty raw string; a present zero record is invalid even beside a valid companion. Closed validation requires complete effective Errors before-policy, genuine unsupported raw severity, matching positive IDs and a canonical desired Quality choice or actual rule removal. Absence never creates a Quality record. Detailed output orders enforcement, Required approvals, then Quality and labels removal inactive; status-only still omits all records and object context. The aggregate is presentation evidence, never mutation input, and strict raw response/fresh-GET verification remains independent. See the [Quality contract](../settings.md#ruleset-quality-severity-observation-normalization).

Normalized Required approvals uses a separate concrete integer record and optional `required_approvals_normalization` member. Decode required `path`, `raw_value` and `fallback` through typed pointers so missing/null differs from zero; reject fractions, strings, overflow and unknown members, assigning only after success. Closed reconstruction requires effective 0 before-policy, a genuinely out-of-range raw integer and a desired UI count 0–10 or complete PR-rule removal. Each present zero metadata object is invalid even beside valid companions. The fixed aggregate retains all three records; presentation and independently optional typed warning sinks order enforcement, Required approvals, Quality. Strict original-response/fresh-GET verification confirms counts or actual rule absence; projection cannot supply successful verification values. Existing collection count one and status-only privacy remain. See the [Required approvals contract](../settings.md#ruleset-required-approvals-observation-normalization).

Normalized Allowed merge methods use an Action-local `merge_methods_normalization` DTO with a string `path` and present typed string arrays `raw_value` and `fallback`. Reject missing/null/wrong-type members, case aliases and unknown keys at decoding; closed reconstruction rejects empty lists, duplicates, canonical-only raw values, altered defaults and ID/policy conflicts, independently of valid companion records. The writer and reconstructed display own both arrays. Raw order remains intact, desired choices render in named UI order, and actual PR-rule removal has no invented after-list. Metadata is presentation data only, never acquisition proof or apply input. Collection count one and status-only privacy remain unchanged. The [Allowed merge methods contract](../settings.md#ruleset-allowed-merge-methods-observation-normalization) owns product semantics.

Normalized bypass modes use an Action-local `bypass_mode_normalizations` DTO on existing `rulesets` entries. The optional pointer-to-list distinguishes absence from present-empty evidence. Each record requires `actor_type` and closed string `normalization` (`path`, `raw_value`, `fallback`); numeric `actor_id` is omitted for nil identity. Recursive null/case-alias rejection and strict unknown-field decoding still apply. Domain reconstruction requires exact actor identity bound to effective `always` before-policy, unsupported raw mode, consistent selected Ruleset IDs and a valid desired whole object. Reject empty, forged or duplicate records even beside valid scalar companions. An empty raw string remains acquired evidence.

The writer and validated display own their slices and ID pointers. Presentation and typed diagnostics use one owned ordering operation: enforcement, Required approvals, Allowed merge methods, Quality severity, then actor type and numeric ID. Desired UI mode or actual actor removal stays write-required; detailed Summary escapes values and status-only hides all policy/provenance. Collection count remains one. Report consistency does not prove complete API acquisition and never supplies apply input or raw verification. See the [bypass-mode contract](../settings.md#ruleset-bypass-mode-observation-normalization); #481 remains separate.

Normalized Environment mode entries carry optional concrete `deployment_mode_normalization` on the existing `environments` collection. Require string path/fallback and both nested boolean `raw_policy` members, preserving explicit false and rejecting null/missing/type/unknown members atomically. A present zero record fails closed. Reconstruction requires an update with exact existing name identity, complete effective declared-null before-policy, genuine equal raw booleans and explicit canonical mode request; acquisition completeness remains state-owned and is not reconstructed from the report. `before` is effective policy for all Environment entries; `after` stays the actual partial request with no invented defaults. Latent patterns remain outside report policy. Shared rendering keeps scoped warning/decision, effective-before label, API-controlled omission note, HTML escaping and status-only privacy. Existing collection count remains one, not completion of #481. Reports are never apply or raw-verification input.

Normalized Environment ref-type updates carry optional `pattern_observations` on the same name-bound entry. When present, it is the complete owned acquired list, including canonical companions and positive unique pattern IDs; at least one entry has a genuine unsupported-string normalization. Each entry contains its effective `pattern` and an optional closed `ref_type_normalization` with required string `path`, `raw_value` and `fallback`. Empty raw strings remain valid; missing/null members, forged or zero records, wrong identities and duplicate raw pairs fail. Desired `after` must explicitly own the pattern list, including an empty list. Omitted lists carry no pattern evidence or warnings.

Reconstruction requires canonical Selected before-mode and excludes `deployment_mode_normalization` on the same entry. A unique projection must match the complete effective before-list. A genuine projected collision requires that effective list to be absent while all distinct acquired identities remain in `pattern_observations`; absence is not interpreted as an empty collection. Serialized evidence validates presentation consistency but cannot prove that API acquisition was complete. Detailed output retains scoped warnings, one write-required collection decision and canonical companions; status-only hides the object and provenance. IDs and raw records never enter public YAML or apply input. See the [ref-type contract](../settings.md#environment-ref-type-observation-normalization).
