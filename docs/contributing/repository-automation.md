# Repository automation

This guide is for maintainers of **daiksud/gh-settings**. For installing gh-settings workflows in another repository, use the [GitHub Actions guide](../github-actions.md) and [examples](../../examples/github-actions/README.md). The public guide explains [how to protect the apply path](../github-actions.md#protect-the-apply-path); this page maps those responsibilities to this repository's workflows and controls.

The workflow files describe source-controlled behavior. Required reviews/checks, Environment protection rules, App installations, secrets, and event-policy eligibility are configured separately on GitHub; inspect those settings when assessing the current operational state.

## Workflow inventory

| Workflow | Trigger and responsibility |
| --- | --- |
| [`ci-pr.yml`](../../.github/workflows/ci-pr.yml) | PR creation, push, reopening, and base edits run code validation; metadata-only edits do not alter the reported `pass` result |
| [`prlint.yml`](../../.github/workflows/prlint.yml) | PR creation, push, reopening, and edits validate the current title/body through `pr-message` |
| [`ci-push.yml`](../../.github/workflows/ci-push.yml) | Pushes to `main`; validate source and the built candidate, ending in `pass` |
| [`labeler.yml`](../../.github/workflows/labeler.yml) | PR-target events suggest add-only labels for unambiguous all-files path categories without executing candidate code |
| [`settings-pr.yml`](../../.github/workflows/settings-pr.yml) | Relevant PR path changes; read-only settings plan and review Summary |
| [`settings-plan.yml`](../../.github/workflows/settings-plan.yml) | Dedicated manual main-only declared-settings observer; inactive until separately approved Environment/credential activation |
| [`settings-main.yml`](../../.github/workflows/settings-main.yml) | Pushes to `main` affecting settings or this workflow; one Environment-bound direct apply job |
| [`settings-environment-guard.yml`](../../.github/workflows/settings-environment-guard.yml) | PR target events and pushes to `main`; inspect workflow YAML with trusted source, reporting `gh-settings` |
| [`approve-codex-review.yml`](../../.github/workflows/approve-codex-review.yml) | Codex summary updates or successful PR CI completion; conditionally create a bot approval |
| [`release.yml`](../../.github/workflows/release.yml) | Explicit manual dispatch from `main`; shared resolve, commit, acceptance, release, and verification orchestration delegates product work to local Actions |

Release publication has no Issue-comment bridge. The owner starts [`release.yml`](../../.github/workflows/release.yml) directly with `workflow_dispatch` after main verification; version calculation happens within the workflow. This repository's other `issue_comment` workflows do not authorize or dispatch releases.

## PR lifecycle

A code-changing PR event marks `pass` pending, sets Draft, resolves the static build and acceptance matrices, runs commit-stage, then marks the PR Ready before process and public-Action acceptance. Both acceptance legs verify the same manifested binary from commit-stage without rebuilding it. The final API-only reporter succeeds only when every prerequisite succeeded; GitHub triggers, concurrency, and protection own revision freshness and merge eligibility. A title/body-only edit skips this path without writing a new `pass` status or repeating Draft/Ready changes. Metadata edits use a different concurrency group so they do not cancel code validation.

The independent `pr-message` job checks the current title and body together as the proposed squash message. GitHub's required-check settings enforce this separately from the code reporter; the reporter does not query or enforce rulesets. See [PR validation](pr-validation.md) for the independent checks, metadata separation, and failure behavior.

Jobs executing PR source have read permissions, no supplied secrets, and no persisted checkout credentials. Draft/Ready and code-status jobs have narrowly scoped write permissions but do not check out or execute PR code, local composites, or transferred artifacts. Fork token restrictions can block automatic state/status changes; the workflow does not bypass them.

This validation pipeline does not merge, publish, or deploy. Use [testing](testing.md#ci-validation) to interpret its results. GitHub's protected-main and Environment configuration determine whether a reviewed change can reach apply; a passing source test does not configure those controls.

## Protected main and required checks

The [declared default-branch Ruleset](https://github.com/daiksud/gh-settings/rules/24911852) selects the existing Ruleset by ID in [settings.yml](../../.github/settings.yml): one approval, stale approval dismissal, mandatory CODEOWNER approval, resolved review threads, signed and linear history, and strict required checks. The declaration retains the existing `pass`, `gh-settings`, and `pr-message` contexts while their separate check-name migration is pending. Repository merge configuration allows squash only. No bypass actors are configured, including administrators. Every change must satisfy the ordinary approval, CI, signature, and resolved-thread rules; see the [review policy](../../AGENTS.md#code-review). This declaration is applied by the trusted main workflow only after merge; verify the actual live Ruleset and Actions permission after application rather than assuming that this file is already enforced.

| Required check | Source and purpose | Limit |
| --- | --- | --- |
| `pass` | [PR code CI](../../.github/workflows/ci-pr.yml) reports source, commit, and both acceptance matrix results; metadata-only edits do not overwrite it | PR source controls its tests and CI; a successful result is not independent authorization for privileged code |
| `pr-message` | The [independent PRLint workflow](../../.github/workflows/prlint.yml) checks the current title/body separately from code validation | Syntax validation does not establish semantic type, coherent scope, or disclosed compatibility impact |
| `gh-settings` | The [trusted guard](../../.github/workflows/settings-environment-guard.yml) uses main-branch policy to inspect candidate workflow YAML as data | It checks the limited Environment/trigger/name policy below, and the required check's app/name does not identify a unique workflow |

See [required-check setup](../github-actions.md#protect-main-with-required-checks) for branch freshness and trusted check-source requirements. Requiring these names from GitHub Actions does not by itself prove that their intended workflows evaluated the proposed change.

After a permitted merge, a matching main push starts the settings workflow. Whether the selected Environment adds a separate deployment approval depends on its live reviewer configuration. If PR review is intended to be the only manual approval, apply the [documented conditions for that mode](../github-actions.md#when-pr-review-is-the-only-manual-approval) and [verify the protection](../github-actions.md#verify-the-protection-before-use), including check-source identity. Neither a source comment nor `environment: gh-settings` establishes whether a reviewer gate is currently enabled.

## Active settings workflows

The active callers use independently pinned released packages; see the [published package and consumer pins](../github-actions.md#published-package-and-consumer-pins) for adoption requirements. Their pins are independent of the local development [`action/cli-version`](../../action/cli-version); the invoked published tag or its matching pinned SHA selects the CLI. Publishing a release or changing examples does not automatically update these callers.

The PR caller uses trusted default-branch `pull_request_target` code for opened, synchronize and reopened events targeting main. Its path filter covers `.github/settings.yml`, both operational caller workflows, and the GitHub Actions examples. The exact main-ref/repository/base condition and Environment `gh-settings` constrain this credential consumer. Per-PR concurrency cancels superseded plans.

Before minting a token, the caller anonymously verifies this public repository's fixed identity, fetches only filtered commit/tree metadata for the event's PR head, and downloads the single regular `.github/settings.yml` blob. It validates the fetched head, file mode, bounded size and Git blob hash. It creates a configuration-only consumer with candidate Git identity; no PR code, hooks, local Actions, dependency configuration or scripts are checked out or executed. Public API rate limits, a visibility/identity change, an unavailable blob or a moved PR head fail the preparation; there is no credential fallback. This public-only retrieval deliberately needs no Contents grant on ANSWER26.

The plan job then mints a short-lived repository-scoped token from the same ANSWER26 App used by main apply, requesting Administration write and Issues read, and passes it explicitly to the pinned released Action. GitHub's [Ruleset GET contract](https://docs.github.com/en/rest/repos/rules#get-a-repository-ruleset) returns bypass actors only to callers with Ruleset write access. Nonmutating plan therefore needs a write-capable token for complete observation; it is not a read-only credential. This token can change repository administration settings if trusted executing code misuses it. The existing installation grants are unchanged, and its repository selection is limited to this repository. No additional Environment consumer or API mutation is authorized by this permission request. Feature adoption must still verify complete observation, endpoint support and installation permissions; the broader token alone does not establish that a Ruleset is safely manageable. Local fixtures establish data isolation and failure handling, not effective remote grants or successful live execution. A PR changing this caller itself runs the previous default-branch caller; subsequent relevant events must verify the updated trusted plan.

The main caller runs only on a push to `main` changing `.github/settings.yml` or `settings-main.yml`. Its single `apply` job references Environment `gh-settings` and contains three steps: checkout of the triggering `github.sha`, App token creation, and direct apply. Repository-scoped concurrency does not cancel an in-progress apply.

The token-creation step references `vars.ANSWER26_CLIENT_ID` and `secrets.ANSWER26_PRIVATE_KEY`, limits installation scope to the triggering owner/repository, and requests Administration write and Issues write. The resulting token is passed only to the Action's apply input; the token Action owns its normal post-job revocation. Source checks verify those bindings, not the remote App installation or actual token revocation.

The operational callers manage the twenty existing labels in [this repository's configuration](../../.github/settings.yml) by their verified numeric IDs, with every supported value explicit. Unlisted objects remain unmanaged and are never implicitly deleted. The main caller requests Issues write for label mutations; installation grants are unchanged. This permission also permits operations on issues, comments, assignees and milestones. See the [label permission contract](../github-actions.md#labels-and-permissions) before changing label definitions or token requests.

When the fresh labels comparison performed by apply has no operations, that invocation sends no label mutations. An earlier zero-difference PR plan does not guarantee that result: labels can change before apply reads them. It also does not make the whole apply write-free, because declared repository fields and topics retain their direct PATCH/PUT behavior. A labels read or mutation failure occurs after those earlier writes and does not roll them back. Any claim that an adoption or run performed no label writes needs evidence for that exact execution, not just a prior plan or the generic success message.

There is no prepare/handoff job or main-side pre-approval plan. The PR Summary and exact committed configuration provide review context; direct apply does not consume a saved plan and may overwrite intervening changes to managed values. The presence of `environment: gh-settings` identifies the selected Environment but does not establish whether reviewers are currently configured.

## Active repository Environment guard

The [guard workflow](../../.github/workflows/settings-environment-guard.yml) checks out trusted `main` policy into `.policy` and the candidate PR merge into `.candidate`. The candidate is inspected only as YAML data. The job has a read-only token, installs Go using trusted configuration, and runs the main-branch [scope test](../../tests/github-actions/settings_environment_scope_test.go) with `GH_SETTINGS_WORKFLOWS_DIR` pointing at the candidate workflows.

The `gh-settings` Environment allowlist contains exactly two locations: `.github/workflows/settings-main.yml/jobs.apply` on push to main, and `.github/workflows/settings-pr.yml/jobs.plan` on trusted `pull_request_target` targeting main. The PR job must have the exact event/main-ref/repository/base condition, and only opened/synchronize/reopened activities are permitted. All other `gh-settings` references are rejected. The existing main reference remains mandatory; the new PR reference may be absent while the guard is deployed before its caller, but absence cannot grant another path access. Dynamic Environment names, workflow/job aliases or merges, duplicate mapping keys, dynamic job names and job-level reusable-workflow calls remain rejected. Unrelated literal Environment names and the separately gated inactive `gh-settings-plan` observer retain their existing boundaries.

The guard was deployed before the operational PR credential consumer. GitHub [evaluates `pull_request_target` using the default branch](https://github.blog/changelog/2025-11-07-actions-pull_request_target-and-environment-branch-protections-changes/), including Environment branch matching; existing main-only deployment restrictions do not need to be widened. The permitted PR job still needs trusted executing code and candidate YAML treated only as data; path/event allowlisting does not inspect every step body. The allowlist does not configure live Environment restrictions or issue tokens itself.

The guard does not inspect the allowed apply job's step bodies, approve Action revisions, restrict its API operations, validate actual token grants, or configure remote Environment/ruleset settings. The allowed job could still be changed to execute code with privileged credentials. Review that job, its referenced code, and changes to the guard/policy itself under the [apply-path protection guidance](../github-actions.md#protect-the-apply-path); later runs use whatever policy has been merged into `main`.

The dedicated check name is **`gh-settings`**. The policy reserves that job ID/display name for the guard and rejects collisions elsewhere in inspected workflows. The ordinary Go suite also runs the scope assertion and contributes to `pass`.

These checks detect violations in the inspected source, but the required status name does not identify a unique workflow. GitHub documents that [required checks do not take the workflow or event trigger into account](https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/troubleshooting-rules#troubleshooting-required-status-checks). Selecting GitHub Actions as the required check provider identifies the app, not this guard's workflow file. Another Actions job can report the same name, so a green `gh-settings` result alone is not proof that the trusted guard ran. The name-reservation test prevents collisions only when the trusted policy actually executes.

When evaluating enforcement, inspect the applicable required checks and allowed check providers, actual guard run, Environment deployment branches/reviewers, and [`pull_request_target` event policy](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target). The repository YAML does not establish those external settings or enforce policy across other repositories. This guide records the guard's behavior and limits without prescribing a change to external approval configuration.

## Candidate settings preparation (not activated)

The standalone [pr-settings helper](../../scripts/pr-settings/main.go) prepares candidate data for a future trusted observer. No current workflow calls it, selects a new Environment or supplies App credentials. Its implementation does not authorize activation, release publication, credential exposure or token issuance.

Build the helper from a reviewed, exact main revision in a separate trusted source directory. Invoke it from the canonical `GITHUB_WORKSPACE` root, which must not already contain `.git` or `.github` or be inside another Git repository. The trusted source can be under `.trusted`; it must never be PR source. Set an existing ordinary workflow read token in `GH_TOKEN` and an absolute `RUNNER_TEMP` on the same filesystem as the workspace. Contents read, Pull requests read and automatic Metadata read suffice for these preparation APIs; no App token or setting-write grant is needed. The helper does not issue tokens or inspect their actual grants.

The command interface is `pr-settings prepare PR_NUMBER EXPECTED_HEAD_SHA`, then `pr-settings verify PR_NUMBER EXPECTED_HEAD_SHA` after the caller's plan. PR numbers are positive canonical decimal integers and expected heads are full lowercase 40-character hex SHAs. There is no target, URL, file-path, command or Action override. The target is this repository's fixed name and repository ID, with base branch `main` and path `.github/settings.yml`. Public visibility is required because Git metadata is fetched anonymously; visibility changes require a separate design rather than a credential fallback.

Preparation requires an open, same-repository PR with a calculated mergeable test-merge commit; forks, pending/conflicted merges, wrong identities and missing fields fail closed. Git reads fetch commit/tree metadata only with `blob:none`, without checkout, hooks, submodules, credential helpers or inherited Git configuration. Unexpected downloaded blobs are rejected. The real test-merge object's ordered parents must match the observed base/head. Native tree entries must identify a `.github` tree and a nonexecutable regular `settings.yml` blob; symlinks, submodules and missing paths are rejected.

Only the selected blob is read through the fixed GitHub API, with redirects forbidden, a 2 MiB response bound, a 1 MiB configuration bound, and base64/size/Git-object-hash verification. YAML is handled only as bytes at this stage. The future caller must run published configuration validation before requesting any privileged credential. No candidate workflow, script, local Action, attribute filter, build, cache or artifact is executed or restored.

The prepared root contains real candidate Git metadata with the fixed origin and actual merge HEAD, plus only the candidate settings file. A private `.git/gh-settings-plan.json` receipt records verified revisions and blob/content digests; it contains no token or policy values. New directories use mode 0700 and settings/receipt files use 0600. Existing destinations are refused rather than overwritten. Staging is removed and newly owned destinations are removed on ordinary preparation failure; filesystem/forced-termination failures are not transactional cleanup guarantees. Successful stdout consists only of target, PR number, head/base/configuration SHAs and configuration SHA-256, never YAML or API/Git diagnostics.

Preparation checks PR/main state again before returning. Verification checks regular local paths, the file against both its SHA-256 and actual candidate Git blob, origin/HEAD/tree/receipt identity, and current PR/main state. A changed head, base or test-merge commit makes the result stale. Call `verify` with the ordinary read token immediately after plan, and require both steps to succeed before accepting an observation. Neither check locks external state, binds a later apply or makes a saved plan executable. The caller owns the private workspace and must not execute untrusted code or allow other steps to rewrite it.

`scripts/pr-settings` fixtures use real synthetic merge/tree/blob identities and bounded read-only API stand-ins. They cover unsafe paths, fork/identity failures, stale revisions, missing/oversized/forged data, local tampering, preservation/cleanup, inherited Git programs/credentials and refusal of redirects. These tests establish preparation boundaries, not App visibility, a live protected workflow or deployment approval. Existing `gh-settings` Environment/guard restrictions and main apply remain unchanged; a protected observer still needs a compatible published private-reporting package and separately approved Environment/guard and credential paths.

## Protected settings plan (source prepared, activation separate)

The [protected manual plan](../../.github/workflows/settings-plan.yml) is a proposed main-only observer for [Issue #380](https://github.com/daiksud/gh-settings/issues/380). It does **not** reuse the existing apply Environment, introduce a required check, automatically change settings, or run candidate PR scripts or workflows. The repository variable GH_SETTINGS_PLAN_ENABLED must be separately set to the literal true to enable execution. Until then, the unprivileged activation gate fails and the protected job is skipped; a no-op run is not a successful observation.

The observer uses an immutable, reviewed Action release; publication does not activate the workflow.

Create a **separate** literal Environment named gh-settings-plan, restrict it to main, and explicitly approve its reviewer and credential policies. Provisioning the existing GitHub App client ID and private key in that Environment requires separate authorization. Do not reuse gh-settings, move the private key into repository-wide secrets, change existing App grants, or assume that referencing an Environment in YAML creates protection. Inspect live branch rules, Environment restrictions, App installation and secret placement before permitting token issuance.

To inspect one reviewed open same-repository PR, manually dispatch the plan workflow **from main** with the PR number and expected full 40-character head SHA. A read-only workflow token obtains the candidate merge metadata. Trusted main code is checked out only under .trusted and compiles the fixed [pr-settings helper](../../scripts/pr-settings/main.go); that helper prepares only the pinned settings blob and real Git revision in a separate data-only workspace. No PR code, Action, scripts, dependency cache or artifact are executed or restored.

Before minting an App token, a separate SHA-pinned checkout of the pinned Action provides the installer. It downloads and checksum-verifies that release's CLI, checks the exact version, privately validates candidate YAML and records only the trusted checkout/CLI metadata required by the Summary. Candidate YAML, parser errors and installer diagnostics remain suppressed. This occurs **before** the job creates its short-lived, single-repository token with Administration write and implicit Metadata read only. It deliberately omits Issues write.

The token is passed solely to the verified CLI's fixed read-only `action plan` command. Raw command output and API diagnostics are suppressed. Changed, no-difference and the closed validation/target/read failure cases write an owner-only typed report; the workflow preserves the command's original status separately. An unexpected command failure without a report returns a fixed public error and stops. The ordinary read token then re-verifies the PR head, base, merge commit and configuration bytes. A stale or unreadable candidate fails before any Summary is rendered. Only a fresh report reaches the credential-free detailed Summary renderer. Its metadata identifies the target, PR, head, base, prepared merge/configuration, workflow, Action/CLI and configuration digest. Changed and no-difference results succeed with distinct content; invalid, target-failure, read-failure and incomplete-observation reports write their closed error state before the original failure is returned. Values appear only for explicitly declared settings; v0.18.1 projects retained Ruleset state to that declaration while preserving the complete remote object for a later direct mutation. Tokens, raw server errors and omitted settings do not enter logs, outputs or the Summary.

The private plan file is removed with its temporary CLI directory and prepared candidate on ordinary exit. Normal Action post-processing owns App-token revocation. Abrupt runner termination can prevent cleanup or revocation. These reads are not atomic locks and cannot authorize a later apply.

A successful workflow and its Summary now distinguish a complete fresh comparison from failed, incomplete or stale work. That source contract does not prove the dedicated Environment's live restrictions, the App's actual visibility or token revocation, and it does not activate the workflow. #380 retains those separately approved operational gates before #381 can consume real observation evidence.

The [trusted Environment guard](../../tests/github-actions/settings_environment_scope_test.go) reserves the settings-plan check name, rejects unauthorized references to the new Environment, and requires manual-only dispatch with the literal repository/main/activation gate. The [plan workflow tests](../../tests/github-actions/settings_plan_test.go) check input binding, trusted-only checkout, step sequence, SHA pins, token/secret boundaries and behavior for declared differences, no difference, validation/API failure, partial observation and stale candidates. They also require freshness before Summary rendering and fixed public diagnostics without unmanaged values or credentials. Local fixtures prove source structure and shell behavior only, **not** live Environment protection, release downloads, App token grants, complete private-policy visibility or actual revocation. Do not close #380 until its separately approved operational checks have succeeded.

For activation, explicitly approve and configure the dedicated Environment, approve credential exposure, verify its restrictions, enable the repository variable, and run one pinned test PR without settings mutations. Confirm the declared-only Summary and failed/stale outcomes with the real App's existing grants before treating the observer as complete. Do not add an automatic PR trigger or another required check in this work. To roll back, disable the variable first, revoke the observer token/credential exposure and review removal of its workflow/guard. Leave main apply, its Environment and the existing setting values untouched.

## Codex approval control

The [approval workflow](../../.github/workflows/approve-codex-review.yml) reacts to trusted summary updates from `chatgpt-codex-connector[bot]` and rechecks the most recent summary after successful PR CI completion. It reads the structured Codex review state, requires both **Code Review** and **Security Review** to have completed on the *current exact PR HEAD*, rejects unresolved findings, and requires Codex's 👍 reaction. It waits up to three minutes for a delayed reaction, refuses draft/closed/stale heads, avoids a duplicate same-HEAD bot approval, and submits an approving GitHub Actions review tied to the verified SHA.

The workflow runs trusted default-branch code without checking out PR source. GitHub Actions must be permitted to approve PRs, and a submitted approval is distinct from Codex's comment/reaction or workflow success. Recheck live Ruleset approvals, any review threads, and required CI for the final HEAD. No administrative bypass is permitted; an unavailable reviewer leaves the PR blocked until an eligible approval is obtained.

## Inspect external configuration

Use [repository rules](https://github.com/daiksud/gh-settings/rules), [Environments](https://github.com/daiksud/gh-settings/settings/environments), and [Actions settings](https://github.com/daiksud/gh-settings/settings/actions) when diagnosing blocked or unexpected execution. Follow [verification before use](../github-actions.md#verify-the-protection-before-use): confirm the required check results and their actual workflow/source for the intended commit, the selected Environment's branch/tag and reviewer restrictions, bypass settings, App installation/credential bindings, and whether GitHub permits the workflow event.

[Operational fixtures](../../tests/github-actions/operational_test.go) and the [test evidence boundaries](testing.md#release-and-publication-evidence) help distinguish source correctness from those external settings. Release dispatch and recovery have their own [maintainer runbook](releases.md).
