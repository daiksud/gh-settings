Status: implements named policies (#352), custom deployment branch/tag patterns (#353), and typed administrator-bypass management. Historical [ADR 0029](../adr/0029-environment-ownership-and-protection.md) records an earlier proposal; the current contract is [Environments](../settings.md#environments).

## Ownership and API-controlled omissions

Public entries live under `repository.settings.environments`. Only listed names are managed. Omitted and empty collections select no objects and make no Environment requests. Names select ordinary REST create-or-update, not numeric identity. Changing a name selects another object; the old unlisted object remains. Deletion, rename, secrets, variables, deployment execution and numeric-ID writeback are outside this feature.

Each listed policy owns supported settings as a whole, delegating omitted built-in request fields to GitHub rather than supplying client defaults or copying old values. Plan labels the effective before policy and displays the partial request with an API-controlled outcome warning. A partial request remains an update intent; full explicit matching requests can be no-ops. Readback verifies explicit requested values, not presumed omission outcomes. A name-only declaration sends `{}`, not a read-only existence assertion.

Names use documented client Unicode simple folding, preserve display spelling, reject controls/surrounding whitespace and encode slash/percent as one path segment. Reviewers are at most six unique typed positive numeric references, sorted independent of response order. GitHub validates principal access and account eligibility; this client never grants access or resolves a reused human name to a different principal. True self-review prevention cannot accompany an explicitly empty reviewer set. Public `deployment_branches_and_tags` selects `no_restriction`, `protected_branches_only` or `selected_branches_and_tags`; API null/boolean-pair aliases are not public YAML. All public nulls are invalid. `deployment_protection_rules` contains optional `wait_timer` (0–43200), `required_reviewers` entries selecting one positive `person` or `team`, `prevent_self_review` and `allow_administrators_to_bypass_configured_protection_rules`.

## Typed deployment patterns

`deployment_branch_or_tag_rules` is a separate authoritative collection of case-sensitive `(ref_type, name_pattern)` identities. `ref_type` is `branch` or `tag`; raw API type/name/ID fields remain internal. Branch and tag may share a name; duplicate pairs are invalid. API IDs stay internal. List omission sends no pattern CRUD, because the Environment PUT has no pattern-list field; the client does not synthesize an empty collection or predict mode-transition effects on inactive patterns. Explicit `[]` removes every observed pattern. An explicit list requires selected-branches-and-tags mode (internal custom mode), either explicitly selected or completely observed on an existing Environment.

Custom-mode reads require all pages, stable total count, unique positive IDs, typed nonempty names, and unique pairs. Missing `type` is an error even though some official examples omit it. A read-only request to this repository's existing Environment returned `type: branch`; this does not prove all servers, grants, modes or writes behave identically.

## Complete reads and unsupported settings

Inventory requires explicit total count, complete pages and unambiguous names/IDs. Selected existing names receive individual detail and enabled-custom-protection reads. Unlisted details are not acquired by plan/apply; export explicitly selects every name. Failed/hidden reads never become absent objects. Detail 404 after inventory is a read failure, not create permission.

An explicitly present complete `protection_rules: []` represents no enabled built-in rules. Missing/null containers are errors. Present timer/reviewer rules require their complete typed values, including false/zero/empty. Missing policy is not null. An explicit root `can_admins_bypass` boolean is required for a complete observation; neither an absent nor a null/malformed value implies false or true. Unknown rule kinds/fields, enabled custom deployment rules and other unsupported root settings fail rather than being silently erased. Read-only principal profile metadata is reduced to its typed numeric reference; Environment URLs/timestamps/internal IDs do not enter writable policy.

The explicit UI administrator-bypass checkbox translates to native API `can_admins_bypass`, including false. Omission sends no field and supplies no true/default value. Export and plan carry observed false/true values; apply verifies a requested value in fresh typed readback. Request spelling is supported by the pinned [go-github implementation](https://github.com/google/go-github/blob/6eccc42c1ea8cd175b190f8e785d1a55656e3c49/github/repos_environments.go), independently of that library's default-inserting marshaler. The client uses its own omission-preserving payload and does not copy arbitrary response fields into a mutation. The REST documentation's incomplete parameter table is not treated as proof of server behavior.

An explicitly authorized 2026-10-27 live characterization used one uniquely named temporary Environment in a public, personally owned GitHub repository, with API version `2026-03-10`. Explicit false and true each returned HTTP 200 and matched fresh GET. With timer zero, self-review false, reviewers empty and branch policy null held constant in the requests, subsequent flag omission retained each preceding false/true value. Other observable fields stayed equal. Creation without the flag returned true in this one test; the client still does not encode that as a default. The newly created ID was checked before HTTP 204 deletion, absence was verified, and pre-existing Environment observations/inventory matched before and after. No deployment, workflow, secrets or permissions were created, and no effective administrator-bypass attempt was tested. These results support the tested writable field; they do not generalize omission or entitlement guarantees to all requests/servers.

## Apply and reporting

Local validation precedes remote work. Apply acquires complete policies for selected names after earlier resources, then writes in stable name order. Each adapter call rechecks repository identity/archive state and selected protections, skips a fully explicit fresh match, and sends specified built-in fields without name/ID/pattern-list metadata. After PUT, explicit patterns are freshly read, missing pairs created, then obsolete pairs removed after rechecking their API ID and typed name. Complete fresh readback must agree with the requested fields/list. A 303 create response is an error, never permission to follow a redirect or adopt an unknown object.

Ordinary upsert is intentional: concurrent name creation/update is not rejected by an invented create-only rule, and a different numeric Environment incarnation is not a declaration identity mismatch. There is no lock, transactional snapshot, atomic policy replacement, rollback or hidden retry. Earlier successful writes remain applied when a later read/write fails. Prerequisite failures are classified before-write; PUT, malformed response, mismatched/denied readback failures may have applied.

Plan and Action reports show complete selected effective before policies and actual requested after policies, identifying API-controlled omissions instead of fabricated resulting values. A nonempty collection counts once. The same-version report rejects incomplete observations, null/unknown request fields, invalid deletes, wrong identity, duplicate/unordered changes and inconsistent outcomes/counts. The private report keeps internal nullable API policy distinct from omitted intent; public YAML expresses no restriction with its explicit UI choice, not null. Full UI object/report rendering remains #481. Summary escapes content; status-only mode validates the same report without exposing names or policy.

Explicit `export --environments` saves supported observed policies and complete typed patterns in custom mode only after successful reads. Normal export retains its scope. Export has no Environment/pattern IDs and an unchanged complete exact canonical export should produce zero differences; a normalized mode fallback remains actionable. Inactive-mode patterns are not inferred. Malformed, unavailable and other unsupported policies fail before file replacement. Apply never changes caller YAML for Environments, including local/default, opt-out and Actions execution; there is no automatic commit/push.

## Primary API evidence and limits

- [REST Environments](https://docs.github.com/en/rest/deployments/environments): paginated inventory, individual detail and name-addressed create-or-update; timer 0–43200, at most six typed reviewers and nullable branch policy. Reads require Actions read, mutations Administration write.
- [Enabled custom deployment protections](https://docs.github.com/en/rest/deployments/protection-rules#get-all-deployment-protection-rules-for-an-environment): separate complete custom-protection check for selected existing objects.
- [Deployment branch policies](https://docs.github.com/en/rest/deployments/branch-policies): separate paginated typed-name collection, custom-mode requirement and CRUD permission/status contracts. Pattern list omission is not a supported Environment PUT field.
- [Managing environments](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments): case-insensitive names up to 255 characters and lifecycle consequences.
- [Deployment availability/effectiveness](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments): account/visibility restrictions and protected-branches behavior. No subscription, visibility, credential or permission expansion is attempted.

Fixtures prove client serialization, parsing and failure/order behavior, not live omitted-field preservation/reset, entitlements, exact token grants, inactive-pattern retention or effective/intermediate deployment protection. The bounded administrator-bypass experiment above is separate evidence, not a claim that fixtures performed live mutations. Source implementation does not change production Environment policies, establish operational App coverage, or publish a release.

## Rule: Keep raw deployment mode distinct from effective No restriction

- Given a complete typed equal branch-policy pair, project No restriction with independent pair provenance. Valid null is exact; missing/null/type/unknown fields and incomplete acquisition fail without partial observation.
- If raw custom is true, acquire every pattern page and custom-protection check before attaching provenance. Keep latent patterns in separate state; effective fallback neither activates them nor proves Selected applicability.
- Compare only selected names. Explicit mode fallback equality requires one update and scoped UI warning/decision. Every before-object is labeled effective policy; partial request omissions stay API-controlled. Private closed pair metadata, HTML safety, status-only privacy and collection count one remain; #481 is incomplete.
- PUT includes only declared fields. Omitted mode is neither copied nor preserved/certified and emits no unowned diagnostics. An explicitly requested nullable mode must match the raw acknowledgment and independent complete fresh read; canonical acknowledgment followed by retained equal booleans fails with possible write effects.
- Pattern intent under an unknown mode requires explicit Selected. Confirm actual canonical Selected in the intermediate fresh read before ordered create-before-delete CRUD. Neither fallback nor raw custom true is proof. Failed pattern operations retain earlier mode/pattern effects without rollback; earlier resource writes remain reported.
- Pure readers never warn or write; export warns after complete acquisition and preserves destinations on failure. Actual null exports no invented pattern list. Complete #481 reporting remains pending.

## Rule: Keep raw ref-type identity distinct from effective branch

Status: implemented in current source. Complete UI reporting remains #481, and release publication is a separate operation.

- Given complete acquisition of active selected deployment patterns with an unsupported string ref type, export projects that type to `branch` and warns with the Environment name, pattern ID, exact pattern name, original type and fallback. Canonical branch/tag companions remain unchanged and silent.
- Warn in normalized Environment-name order, then ascending pattern-ID order, before materializing or saving the export. Latent patterns under an effective mode other than Selected are neither exported nor disclosed by ref-type warnings. A missing warning sink does not change the effective policy.
- Distinct raw identities that project to the same typed name must not be collapsed. Emit their scoped warnings, fail materialization and preserve the destination. Read failures and incomplete acquisition produce neither fallback export nor ref-type warnings.
- During apply, ref-type warnings require an explicit managed pattern list, the selected Environment name and complete fresh acquisition in canonical Selected mode. Explicit empty lists still own the observed patterns. Omitted lists, unlisted names and latent patterns remain silent; validate the entire raw collection before warning, including when its effective projection collides.
- Given complete unsupported string types, retain original types, case-sensitive names and positive IDs through all pages. Missing/null/wrong-type fields, invalid identities, duplicate raw pairs and incomplete counts fail before publishing any observation or diagnostic.
- An explicit list, including empty, owns raw reconciliation and remains actionable at fallback equality. Plan/private reports/detailed Summary retain the full acquired list and canonical companions; status-only output hides those details. A projected collision is unavailable effective list data, not an empty collection. Collection count stays one pending #481.
- Apply creates canonical pairs before deleting obsolete raw IDs; existing canonical companions keep their IDs. Each removal confirms exact raw ID/type/name. Unsupported/malformed or mismatching creation acknowledgments stop before removal, and final complete readback never accepts fallback equality as canonical confirmation.
- Later failures preserve earlier effects, return nonzero status without success output, retain fresh scoped diagnostics and leave caller YAML unchanged. No corrective retry or rollback occurs. Confirmed canonical repeat is silent and makes no write.
