Use Go 1.25 or later and install [mise](https://mise.jdx.dev/getting-started.html). From the repository root, use the commands below to install the exact tool versions in [mise.toml](../mise.toml), including Go 1.26.0, and run checks through mise so the local versions match CI.

## Shared Go implementation

Published v0.7.0 implements the [v0 simplification contract](concept.md#v0-simplification-contract): one Go implementation serves the CLI and thin composite Action. The [glossary](glossary.md) distinguishes an optional-field declaration, complete observed state and native comparison. YAML/JSON conversion, storage, Git and HTTP stay outside that I/O-free settings model. The examples and active workflows use v0.7.0; this repository keeps its existing `gh-settings` Environment, deployment approval and App credentials until a non-spoofable required PR policy is configured.

The [root entry point](../main.go) binds the CLI/Actions adapters to shared application operations and supplies deferred concrete GitHub read/write functions. Application operations compose workspace and settings behavior; only a needed read/write constructs its API client. CLI owns terminal presentation; Actions owns metadata and typed report/Summary presentation. Metadata uses the shared workspace resolver without a settings operation; Summary renders an existing report without calling plan again. The composite invokes the verified executable directly and keeps only installation bootstrap and necessary Actions wiring. Help/version require no checkout or authentication. Root builds remain `go build .`, retaining `main.version` for `-ldflags '-X main.version=...'`.

## Add an agreed repository field

This is the path for a future approved setting, not permission to add one. First record its meaning, type, omission/null rules and API mapping in the existing [settings contract](settings.md) and affected feature specification. Keep `schemaVersion: 1` and `settings.repository`; the current scope remains five fields.

1. Extend `RepositoryDeclaration` and `RepositoryState` in [the model](../internal/settings/repository.go). Follow the existing optional-pointer declaration and complete-state distinction; omitted values differ from declared false/empty strings. Update presence and comparison owner tests.
2. Extend the private YAML document, decode validation and encode mapping in [the codec](../internal/workspace/config.go). Preserve current aliases/merges and strict rejection rather than adding compatibility parsing. Owner tests cover the accepted type, omission and round trip.
3. Map a complete read into state in [the read adapter](../internal/github/repository.go), and declaration pointers into the private request DTO in [the write adapter](../internal/github/apply.go). Check missing/null/type handling under the agreed API contract and exact declared-only PATCH. Also extend [export's explicit state-to-declaration mapping](../internal/app/export.go), so export includes the new observed value; check that composition at the application owner.
4. Extend [the ordered comparison](../internal/settings/comparison.go), preserving managed count, native values and omission. Review both presentations: the existing CLI renderer accepts ordinary native pairs without per-field dispatch, while [Actions Summary validation](../internal/actions/summary.go) explicitly knows field names/types and currently caps the managed count at five. An accepted additional field must update that contract and its owner tests. Keep the report ephemeral and independent of apply; do not add another planning implementation in shell or the Action.
5. Carry the field through one representative existing [built-product acceptance path](../tests/acceptance), checking the actual interface and boundary payload/output. Update complete-read fixture data where required. Detailed parser/type matrices remain with their owners; add composed wiring cases only when a concrete Actions/caller contract changes. Update the affected settings/command/feature references with the implementation.

For an actual future resource group, agree its semantics first, then place its declaration/state/comparison at the settings owner, YAML grouping at the workspace boundary, endpoint mappings at the GitHub boundary and shared sequencing in the application. Adapt CLI/Actions presentation to those results. The current codec rejects other groups; this describes responsibility, without implementing another group, choosing collection semantics or introducing a registry/resource framework.


## Local process acceptance

Build the product once, then run the tagged Go acceptance tests against that executable:

```sh
mise exec -- go build -o /tmp/gh-settings-acceptance .
mise exec -- go test -tags=acceptance -count=1 ./tests/acceptance -args -binary /tmp/gh-settings-acceptance
```

The [acceptance tests](../tests/acceptance/acceptance_test.go) require an explicit existing binary path and use a local Unix-socket HTTP fixture and go-gh v2.16.2's `http_unix_socket` configuration in a temporary `GH_CONFIG_DIR`. Their dummy token never authenticates with GitHub. Checks cover YAML values, empty strings and false, GET null normalization, current-repository selection, declared-field planning, export → edit → validate → plan → apply, exit codes, stderr, and failure paths. Plan cases verify GET-only access and unchanged configuration; apply cases verify exact PATCH payloads, omission preservation, and no GET. Invalid input and plan/apply with no managed fields make no API request. Temporary repositories/configuration are isolated and cleaned up. Product code needs no testing hook or test-only modification; Unix sockets are required.

[Built-product metadata acceptance](../tests/acceptance/metadata_test.go) checks the actual executable digest/version and a separate committed consumer identity without settings, credentials or API requests. Detailed direct-origin format/scope/isolation checks belong to workspace tests; a representative indirect-origin rejection remains at the real interface. Composed metadata stubs or owned test-executable failure checks exercise wiring gates and are not proof of the installed product's digest. Actual candidate execution establishes that identity separately.

The Linux-only `TestMetadataUsesRunningImage` [regression](../internal/actions/metadata_linux_test.go) launches an owned copy of the test executable and atomically replaces only that child's pathname before requesting metadata. Its digest must still identify the original running image; the parent test runner is never replaced. Other native platforms check an unchanged executable path and do not establish this Linux-specific evidence. Cross-compilation alone does not execute the regression.

[Plan-report acceptance](../tests/acceptance/plan_report_test.go) runs the shared operation through the actual interface and inspects typed JSON/native values and categorical failures. [Summary acceptance](../tests/acceptance/summary_test.go) appends through the actual credential-free entry outside a checkout, checking escaped values, separate identity links and zero API requests. Detailed report/state/storage cases stay in the owning Actions tests. Shared application planning owns validation; its typed failure stages preserve original stderr diagnostics and available target identity without serializing raw errors into the review report. Failed plans remain nonzero after writing a report or Summary; apply never consumes that report.

The [composed tests](../tests/github-actions/composite_test.go) run the real YAML wiring with explicit report fixtures and owned test-executable adapters. They check token-free setup/Summary, explicit execution token, original plan-status precedence and four outputs only after required work. The Go Summary adapter is reused, without a copied renderer or product rebuild. These checks do not establish GitHub Summary publication, Environment enforcement or real token revocation.

## CI validation

The [PR workflow](../.github/workflows/ci-pr.yml) follows Draft → commit-stage → Ready → acceptance-stage and composite-smoke → `pass`. It runs on opened, synchronized, reopened, and edited PRs. The [main workflow](../.github/workflows/ci-push.yml) runs commit-stage → acceptance-stage and composite-smoke → `pass` on pushes to `main`. Failure, cancellation, or skipping either validation job prevents a successful `pass` result. This CI does not merge, publish, or deploy. The ordinary Go test suite includes the [Environment scope assertion](../tests/github-actions/settings_environment_scope_test.go), and the Ruleset-required `pass` fails on unauthorized use. The [trusted-source PR Environment guard](../.github/workflows/settings-environment-guard.yml) separately executes the main-branch test against a PR checkout used only as data. The guard status is named `gh-settings` and the policy checks for name collisions. Neither the existing `pass` nor a newly required GitHub Actions `gh-settings` check is an unforgeable identity: PR workflows can publish a job with the same name. A required organization workflow or a check signed by a dedicated App is still necessary before disabling Environment reviewers. Also account for GitHub's `pull_request_target` event policy.

Both workflows call [commit-stage](../.github/actions/commit-stage/action.yml) for formatting, modules, vet, race tests, GitHub workflow/shell checks, a single product build, and Markdown/local links. Ordinary CI injects the committed `action/cli-version`; release keeps its explicit version input and separate equality guard. The producer exposes its actual checked-out Git SHA, CLI version and binary checksum. PR validation uses the merge source, and both downstream jobs check out that exact producer SHA rather than mixing a merge binary with a head-only Action.

CI installs the same pinned development tools from [mise.toml](../mise.toml) with the official mise Action. The acceptance stage installs only Go from that configuration. Composite smoke also installs that exact Go version, solely to compile the standard-library local API fixture; it installs tools before the candidate curl stand-in enters PATH. Tool caches are disabled so PR jobs do not supply installed executables to later runs. Both downstream jobs download that same run's binary artifact with digest mismatch treated as an error. [Acceptance-stage](../.github/actions/acceptance-stage/action.yml) verifies its SHA-256 and embedded version before launching it as a real process. The tagged acceptance Go tests are compiled separately with caching disabled; the product is not rebuilt and the ordinary Go unit suite is not run again. Artifacts are retained for one day; PR artifacts are not reused by privileged publication or settings workflows.

The separate `composite-smoke` job uses the public Action's supported GitHub-hosted Ubuntu 24.04 x64 runner; the existing stages remain on `ubuntu-slim`. It checks out the producer's exact source into `.action`, verifies the transferred candidate's checksum and the Action checkout's source/version through the [bounded fixture preparation](../tests/github-actions/prepare-candidate-download.sh), then creates a Git consumer tracking only `.github/settings.yml`. The nested `.action` checkout remains separate and untracked. The consumer has no root `action.yml` or `action/` helpers.

A test-only [curl stand-in](../tests/github-actions/candidate-curl.sh) serves only the installer's two fixed versioned asset/checksum URLs from the verified candidate fixture, without network forwarding. Actual local `uses: ./.action` expansion runs the unchanged installer, checksum/version checks, the verified executable’s Go metadata entry and `command: validate` with no token input. No committed version override, public binary/download-URL input or old-release fallback is added. This proves candidate integration before publication, not a real release download or immutable released-asset identity.

The following step asserts all four actual composite outputs against the separate consumer commit/origin and this run's candidate version/checksum, and logs distinct source/consumer roots and SHAs. Missing/tampered artifacts, fixture, composite or assertion failures fail the existing aggregate gate; none becomes skipped success. Inspect the exact-source hosted `composite-smoke` log for actual Ubuntu/`uses` evidence. Local native installer/metadata/validation checks, including simulated runner attributes, remain distinct from that hosted proof. Installer fixtures, Go presentation tests and composed consumer tests retain their own boundaries. Local caller fixtures use candidate package bytes/version, not released-tag bytes. The example and operational caller fixtures now share the single-job apply pattern; the former operational handoff verifier is no longer invoked. No separate fixture-testing framework is required.

Plan runs through the same actual composite with a literal dummy read token and the [fixed local API server](../tests/github-actions/plan-fixture/main.go). Its owned short temporary directory contains the Unix socket, isolated `GH_CONFIG_DIR`, readiness marker and safe method/path log. Only the expected repository GET/read token or PATCH/write token is accepted; both tokens are literal dummy values. Received PATCH JSON is decoded and recorded in owned state for an independent complete-object assertion. Closed loopback HTTP/HTTPS proxies prevent ordinary HTTP transport from reaching an external service; the required socket transport does not use that proxy. No real GitHub token, product transport hook or downstream product rebuild is involved.

The [candidate plan checks](../tests/github-actions/candidate-plan.sh) cover a changed string/false declaration, a local read403, and one committed invalid boolean declaration. They require respective request counts of one GET, one GET and zero requests, with unchanged configuration bytes and commit after every call. Expected-failure calls use step-level `continue-on-error` only with mandatory subsequent assertions of failure and four empty public outputs; normal plan requires success and all four expected outputs. No-difference and unmanaged details stay in their owner tests. The fixture must remain live even for the zero-request case and is explicitly stopped and removed by an `always()` step.

Direct apply runs through the same verified composite and binary with the separate dummy write token. Normal and local write403 cases each require exactly one PATCH and no GET, with the complete received object `{"description":"","has_issues":false}`: native empty string/false and every other field omitted. The write failure must propagate failure and four empty outputs; a failed PATCH attempt does not establish the remote outcome. One committed invalid boolean fails with zero API requests, while `schemaVersion: 1` with `settings: {}` succeeds as a zero-request no-op. Both require the live fixture and no captured PATCH. Successful apply cases require all four identities; every case preserves configuration bytes and commit and requires zero new Settings reviews. Even the no-op retains the composite's explicit token and metadata requirements. The installer stand-in rejects either token variable; existing composed tests own token-free version/metadata/Summary and explicit execution-token boundaries, while bounded caller tests retain their labeled approval/revocation simulations. No platform protection is emulated here.

A finite before/after snapshot of the runner command directory identifies exactly one new nonempty Settings review, excluding previous files and scrubbed upload copies. The checks read the Summary bytes actually written by the embedded Go step, matching consumer/CLI identities, native false, escaped HTML/multiline strings or the categorical failure diagnostic. They do not override the Summary path, rerender a substitute, poll GitHub publication or emulate Actions. Inspect actual exact-source hosted logs for this evidence; successful file rendering remains distinct from published Summary availability and owner approval.

The manual release's read-only `candidate-action-smoke` job uses the same bounded candidate helper with its frozen source, requested/committed version and existing Linux release artifact. It runs actual token-free validate on supported Ubuntu before `publish`, requiring the consumer and all four output identities; publication retains its native acceptance prerequisites and also requires candidate success. [Release gate tests](../tests/github-actions/release_test.go) inspect that source/dependency contract and execute matching/three-mismatch helper cases with local dummy bytes. This is static/fixture coverage of manual-release wiring, alongside regular CI's actual current-source composite execution. An authorized release run's logs establish operational candidate and post-publication evidence; its retained post-publication smoke independently verifies real released downloads. No product rebuild, token minting, live apply or release dispatch is part of these tests.

PR-code validation jobs have read permissions, no supplied secrets, and checkout credentials are not persisted. Draft/Ready control jobs have write permissions but do not check out or execute PR code, composites, or artifacts. Normal fork tokens are read-only, so automatic PR-state changes can be blocked on forks; this workflow does not bypass that restriction.

Markdown checks use the rumdl version pinned in [mise.toml](../mise.toml) and the rules in [.rumdl.toml](../.rumdl.toml). MD051 and MD057 validate local headings/fragments and file links; external HTTP availability is not a CI dependency. mise resolves rumdl, actionlint, and ShellCheck through its standard aqua registry. Go module library dependencies remain in `go.mod` and `go.sum`.

## Release and consumer handoff

The [ordered source-refactoring series](https://github.com/daiksud/gh-settings/issues/133) delivered the implementation now published as [v0.7.0](https://github.com/daiksud/gh-settings/releases/tag/v0.7.0). Current `action/cli-version`, the examples and the active workflows all use that release. Publishing a release or updating examples does not itself apply settings.

| Evidence | What it establishes | Boundary |
| --- | --- | --- |
| Built-product acceptance | The supplied executable runs real CLI/Actions entries against isolated files/Git and a local Unix API fixture. | Dummy credentials/local responses do not prove live API or platform protection behavior. |
| Same-source candidate composite | PR/main CI runs actual root `uses` with the producer's exact source/version/artifact and verifies real outputs, plan Summary bytes and direct PATCH behavior. | The bounded download fixture is not a published asset; writing a Summary is not proof of GitHub publication or owner approval. |
| Pre-publication candidate gate | Source/fixture tests protect manual release dependencies and identities; an authorized release run must pass actual candidate validate before publish. | Source/fixture checks alone do not establish that a release ran; inspect the exact authorized release run. |
| Post-publication downloads | A separately authorized release's retained smoke checks the published tag source/version and real downloaded CLI against the accepted digest. | Source/candidate tests do not substitute for that run; failed post-publication checks do not authorize changing immutable tags/assets. |

The active [PR](../.github/workflows/settings-pr.yml) and [main](../.github/workflows/settings-main.yml) workflows use the simplified v0.7.0 examples. Main has one direct apply job, retains `gh-settings`, App `answer26` and `ANSWER26_*` credentials, and no longer has a prepare/handoff step. The [trusted-source PR scope check](github-actions.md#active-repository-environment-guard) improves detection but does not replace deployment approval by itself. Keep Required reviewers until an independently enforced, non-spoofable status or required workflow is configured, and retain the `main`-only deployment restriction and existing `pass`/PR review requirements. Tests cannot prove remote Environment configuration or token revocation. Future releases remain separately authorized.

## Codex approval control

The separate [approval workflow](../.github/workflows/approve-codex-review.yml) requires a Codex summary showing both Code Review and Security Review as Completed and a Codex 👍 reaction to the PR body. It waits up to three minutes for that reaction, then may create a bot Approve. It runs trusted default-branch workflow code without checking out PR code.

This mechanism does not verify the reviewed HEAD or latest Ready-triggered review cycle, and can reuse older completion/reaction information. A successful workflow run alone does not prove that an approval was created. Inspect new Ready-triggered reviews separately. PR body edits also start the CI state sequence again, even when the HEAD has not changed.

The approval workflow becomes available for comment events only after it exists on the default branch. For this workflow to create an approving review, repository settings must allow GitHub Actions to create and approve pull requests. Verify that setting before relying on the workflow. The workflow does not configure tokens, secrets, Rulesets, branch protection, or whether `pass` is a required check.

## Settings example verification

The [settings examples](../examples/github-actions/README.md) are linted and tested in commit-stage. Ordinary Go tests exercise the actual caller YAML with a mock CLI/download, the actual Go Summary adapter and local approval/token stubs. They cover read-only PR planning and both the example and operational main workflows' single approved job with exactly three `uses` steps and no caller scripts. Separate operational coverage verifies the existing `gh-settings` Environment and `ANSWER26_*` credentials. Focused shell fixtures cover the Action's installation bootstrap. Hosted candidate proof covers validate, plan and direct apply with the bounded local API/dummy tokens, including representative read/write/config failures and empty apply. These fixtures do not prove actual Environment approval, branch/tag enforcement or real token revocation; see [owner setup](github-actions.md#ordered-owner-setup).
